# 설계와 검증 순서

현재 목표는 실제 공개 데이터를 받고 안전하게 로컬 가상 주문을 처리하는 첫 수직 구현이다.
실계좌나 Testnet 주문은 포함하지 않는다. 공개 production 데이터 읽기는 자금을 사용하지 않으며
Testnet의 비현실적인 유동성을 전략 성과로 오인하는 일을 피할 수 있다.

## 모듈 경계

2026-09-29 경계 분리와 향후 배치 기준은 [아키텍처 문서](architecture.md)에 정리한다.

```text
src/apex_flow/
  config.py      설정 검증, 안전한 기본값
  collector.py   공개 WebSocket 수신, 재접속, heartbeat
  storage.py     원본 이벤트·주문·상태 영속화, 프로세스 잠금
  market.py      부분 호가 스냅샷, 데이터 유효성, 기본 feature
  paper.py       지연 IOC 가상 체결, 회계, 진입 제한
  cli.py         CLI 인자/명령 선택
  runtime.py     실행 조립과 작업/보고서 생명주기
  clock.py       UTC/monotonic 시각 분리
  demo.py        오프라인 합성 이벤트 예제
  observability/ 지연 집계와 JSONL 보고서
configs/         비용 및 위험 설정
tests/          결정적인 회계·상태·장애 테스트
```

빈 디렉터리만 미리 늘리지 않는다. 다음 구현 시 risk/features/execution을 별도 모듈로 분리하고,
동일한 주문·체결 인터페이스에 backtest/paper/testnet adapter를 연결한다.
실제 거래 adapter는 paper engine의 IOC 근사 모델과 별도로 설계한다.

## 상태 일관성

주문 상태는 PENDING → FILLED / PARTIAL_CANCELLED / REJECTED / EXPIRED / CANCELLED이다.
부분 체결 후 잔량은 즉시 취소되며 장기 대기 limit order는 없다.
동일 ID의 동일 요청은 DB의 기존 결과를 돌려준다. DB가 journal의 기준이며 메모리 계좌는
커밋 이후 갱신한다. 쓰기 실패/파싱 오류/프로그램 오류는 프로세스를 중단한다.
프로세스 재시작은 미완료 주문을 취소하고 커밋된 포지션만 복구한다.
시장 disconnect는 새로운 호가와 trade/mark 수신으로 건강 상태가 복구될 때까지 진입을 막는다.
가상 reduce-only 매도는 최신 public 호가만 요구한다. public 호가 자체가 오래되면 청산하지 않는다.
이는 paper의 체결 정책이며, 실제 청산은 별도의 계좌/주문 상태 검증이 필요하다.
일일 손실 기준은 매수에만 적용하는 간이 검사다. UTC 날짜 첫 처리 시점의 실현 PnL을
기준으로 이후 실현 변화와 전체 미실현 PnL을 합산한다. 매도 전에 날짜를 갱신하여
날짜 변경 후 청산 손실이 다음 진입 때 기준 재설정으로 사라지지 않게 한다.
정확한 자정 equity 손익, 한도 도달 후 당일 차단 유지, 손실 시 자동 청산은 미구현이다.
연결별 순서만 사용하며 서로 다른 스트림 사이의 글로벌 이벤트 순서는 가정하지 않는다.

실제 주문에는 이러한 로컬 ID 처리만으로 exactly-once를 보장할 수 없다.
전송 전 intent 영속화 → 고유 clientOrderId → timeout 시 UNKNOWN 상태 → 거래소 조회/사용자 이벤트
대조 → 확정 결과 반영이 필요하다. UNKNOWN 주문을 새 ID로 재전송하면 안 된다.
취소 응답 뒤에도 누적 체결량을 대조하고, 재시작 시 계좌·포지션·미체결 주문 reconciliation이
완료되기 전까지 신규 진입을 차단해야 한다. 이 요건을 충족하기 전 실거래 기능을 추가하지 않는다.

## 기대값 가정 검토

승률 0.4, 이익 15%, 손실 5%라는 가정의 산술 기대값은 비용 전 3%지만,
이는 확률·실현 손익·분모가 일관되게 추정되었을 때만 의미가 있다. 증거가 아닌 목표 수치다.
레버리지 수익률과 명목금액 기준 비용을 같은 식에 바로 넣으면 단위가 맞지 않는다.
모든 라벨·비용·기대값은 우선 명목금액 대비 bps 또는 계좌 통화 단위로 통일한다.

시간 제한을 두면 TP/SL 외에도 timeout 결과가 존재한다. 따라서 두 확률의 합을 1로
강제하지 말고 timeout 확률과 조건부 종료 손익도 포함해야 한다. 미체결/부분 체결까지 고려하면
신호 기준 기대값과 체결 조건부 기대값 역시 다르다. maker 미체결은 단순 고정 비용이 아니다.
실현 bid/ask 체결 가격을 사용했다면 spread를 별도 비용으로 다시 빼지 않는다.
손실 표본의 fat tail, 연속 상관, regime 변화 때문에 평균 기대값만으로 파산 위험을 설명할 수 없다.

최근 100개 aggTrade 기준 feature는 시간 고정 윈도우가 아니다. 거래 빈도가 달라지면
포함 시간 길이도 달라진다. 추후 시간 기반 feature와 함께 비교하고 latency는 monotonic clock,
이벤트 시각은 exchange time, 원본 재현은 receipt sequence로 명확히 구분한다.

## 다음 구현 순서와 통과 기준

최신 작업 순서와 완료 기준은 [개발 계획](roadmap.md)에 모은다.
초기에는 수십 분~수 시간 보유하는 전략을 연구 후보로 삼고, 마감된 15분/1시간봉으로
진입을 판단하되 주문/위험 상태는 실시간으로 관리하는 방향을 제안한다.
전략 자체는 아직 미정이다. 박스권 하단 매수·상단 청산·이탈 손절은 예시 중 하나이며,
첫 구현 전략으로 확정되지 않았다. LLM 판단의 역할과 효과도 별도로 비교한다.
이 주기와 예시 전략의 수익성은 검증되지 않았고 구체적인 파라미터도 확정되지 않았다.

클라우드 24시간 운영과 선택적인 웹/GUI를 고려해 매매 엔진은 화면 없이 실행 가능하게 설계한다.
화면은 공통 조회/명령 경계에 연결하고, 화면 종료가 매매 엔진 종료로 이어지지 않게 한다.
GUI와 웹은 필수 구현 범위가 아니며 구체적인 기술은 아직 선택하지 않았다.
의존 방향과 목표 모듈 경계는 [아키텍처](architecture.md)에 정리한다.

캔들 기반으로 진입하더라도 TP/SL 체결 순서를 OHLC만 보고 유리하게 결정하지 않는다.
세부 데이터가 없으면 불명확한 체결을 표시하고 보수적으로 평가한다.
기존 실시간 trade/depth 수집기는 실행 비용 측정에 계속 사용한다.

고레버리지는 위 검증을 대체하지 않는다. 초기 작은 edge는 수수료·지연 추정 오차만으로도 사라질 수 있다.
