# 아키텍처 검토와 확장 원칙 — 2026-09-29

## 판단

현재 규모에서 src layout과 단일 프로세스/단일 종목 구조는 적절하다.
문제는 디렉터리 깊이가 아니라 CLI에 실행 정책이 모이고, 테스트가 CLI의 합성 함수에 의존하며,
시간 표현이 숫자 하나로 섞인다는 점이었다. 이번 작업은 이 세 경계를 먼저 분리했다.

여러 서비스·플러그인 레지스트리·메시지 브로커·빈 strategy/models 폴더를 미리 만들지 않는다.
계층은 유지하되 기능이 생길 때 모듈을 패키지로 확장하는 단일 애플리케이션 구조를 사용한다.

## 요구사항 명확화와 목표 구조

- 매매 전략은 미정이다. 박스권 매매는 사용자가 제시한 예시이며 채택된 전략이 아니다.
  봉 주기·보유 기간·LLM의 구체적인 판단 역할도 고정하지 않는다.
- 클라우드에서 24시간 운영하는 것을 목표로 한다. 웹/데스크톱 GUI는 현황·로그·보고서를
  편하게 조회하기 위한 선택 사항이며, 터미널만으로도 운영할 수 있어야 한다.
- 구조 정비의 권장 방향은 도메인별 기능 모듈을 가진 모듈형 모놀리스와 Ports & Adapters다.
  market_data/trading의 핵심 규칙, application의 실행 흐름, ports의 계약,
  infrastructure의 Binance/SQLite/paper 구현, interfaces의 CLI를 구분한다.
  이는 목표 설계이며 아래의 현재 실제 디렉터리에 아직 적용되지 않았다.

전략 교체는 전략 구현과 설정 선택으로 처리하고, 공통 위험 검사·주문·회계를 다시 작성하지 않는다.
공통 입력에 모든 전략의 feature를 강제하지 않고 전략별 필요 데이터와 준비 조건을 명시한다.
LLM은 외부 판단 제공자로 연결하며, 핵심 매매 모듈이 특정 모델 SDK에 의존하지 않게 한다.

### 선택적 관리 화면의 경계

매매 엔진은 화면 없이 실행되는 서비스로 설계한다. 화면을 닫거나 웹 서버를 재시작해도
매매 엔진의 생명주기가 바뀌지 않아야 한다. 웹 요청/웹 worker 시작마다 엔진을 생성하지 않는다.
운영 엔진은 계좌별 상태 변경의 단일 소유자로 두고 중복 실행을 방지한다.

CLI와 향후 웹 API는 동일한 애플리케이션 조회 계약을 사용한다. 현재 포지션·주문 상태·연결 상태·
지연·실행 ID·갱신 시각을 구조화된 스냅샷으로 제공하고, 로그·거래 이력·보고서는 별도 조회한다.
조회/보고서 생성이 엔진의 실행 루프를 막지 않게 한다. 무거운 보고서는 실행 경로 밖에서 만든다.
현재 Store의 배타 잠금을 사용하는 status 명령은 운영 중 조회 경계로 충분하지 않으며,
읽기 전용 연결/스냅샷 등 일관된 조회 수단을 별도로 설계해야 한다.

원격 조회가 필요해지면 엔진의 조회 경계 앞에 API를 추가한다. 초기 구현은 CLI로 검증하고
웹 프레임워크·프런트엔드·별도 프로세스 통신 방식은 지금 확정하지 않는다.
향후 제어 기능을 선택하면 인증·권한을 가진 명령 경계로 전달하고 엔진에서 검증·처리한다.
화면이나 API가 주문/계좌 테이블을 직접 수정하거나 거래소에 별도로 주문하지 않는다.
신규 진입 중지·프로세스 종료·보유 포지션 청산은 서로 다른 명령으로 정의한다.
조회와 제어의 계약 분리가 곧 별도 DB나 전체 CQRS/Event Sourcing 도입을 뜻하지는 않는다.

## 현재 실제 구조

```text
src/apex_flow/
  __main__.py          python -m 진입점
  cli.py               인자 파싱, config/DB 준비, 명령 선택
  runtime.py           SessionOptions와 실행 조립, 작업/보고서 생명주기
  clock.py             TimePoint, Clock 프로토콜, SystemClock
  config.py            비용/위험 설정과 검증
  market.py            시장 상태·신선도·기본 feature
  paper.py             가상 체결·회계·현재의 간이 위험 검사
  collector.py         Binance 공개 WebSocket 수신 어댑터
  storage.py           SQLite 어댑터와 호환 컬럼 추가
  demo.py              오프라인 합성 데이터/시계/왕복 예제
  observability/
    metrics.py         bounded 메모리 집계, 연결 상태, 시계 점프 관측
    reporting.py       실행별 JSONL 저장
```

의존 방향:

```text
CLI → runtime → collector / Paper / Market / observability
CLI → demo
collector → Clock / Metrics / 전달받은 Market·Store·콜백
Paper / Market → TimePoint
Metrics → Clock
JsonlReporter → 파일 시스템
Store → SQLite
```

CLI에서만 argparse를 사용한다. runtime은 SessionOptions를 받아 다른 서비스 실행기로도 호출 가능하다.
Clock은 주입 가능하며 도메인 처리에는 명시적인 TimePoint를 전달한다.
Paper/Market은 보고서 파일 경로·백분위수 집계·WebSocket에 의존하지 않는다.
테스트는 CLI import 대신 demo 또는 해당 모듈의 공개 경계에서 실행한다.

## 아직 완전히 분리되지 않은 부분

- Paper는 Store.db와 SQL에 접근한다. 실거래/Testnet 도입 전에 계좌·주문 repository 경계를 정의한다.
- Market은 Binance payload를 직접 해석한다. 두 번째 수신원이나 replay를 도입할 때
  정규화된 Trade/Book/Mark 이벤트를 도입하고 payload 변환을 어댑터로 옮긴다.
- Paper.step에는 위험 검사·가상 체결·회계가 함께 있다. 전략 도입 시 독립 RiskDecision을 먼저 분리한다.
- collector는 원본 저장/시장 반영의 순서를 조정한다. replay pipeline이 생기면 공통 이벤트 처리기로 분리한다.

이번에 이런 추상화를 전부 추가하면 실제 요구가 없는 인터페이스를 고정할 위험이 있다.
다만 확장 지점은 아래 규칙대로 유지한다.

## 향후 기능 배치

| 기능 | 추가 위치 / 의존 규칙 |
|---|---|
| 캔들 생성·과거 데이터 | market_data/가 필요해질 때 collector/market을 이동하고 import를 일괄 갱신 |
| 전략 구현(미정) | trading/strategies/ — 정규화된 데이터 입력, 구조화된 신호 출력. DB·Binance·CLI 직접 호출 금지 |
| LLM 판단 실험 | 모델 호출 어댑터 + 전략 응답 검증. 시각·유효기간·모델/프롬프트 버전 포함 |
| Risk Engine | risk/ — 수량·한도·청산 정책. LLM 응답에 의존해 손절을 기다리지 않음 |
| paper/Testnet/live | execution/ — 공통 주문 의도/결과 형식. 동일한 체결 보장을 가진다고 가정하지 않음 |
| 과거 재생/백테스트 | backtest/ — 주입한 시계와 같은 전략/위험 로직 사용 |
| 서버 서비스/선택적 UI | 엔진의 생명주기와 화면을 분리. 공통 조회/명령 계약 사용, 전략에 UI 의존성 전파 금지 |

모듈이 커져 서로 다른 책임을 갖게 될 때 나눈다. 파일 줄 수만으로 임의의 계층을 추가하지 않는다.
범용 utils.py에 시간·회계·통신 함수를 섞지 않고, 단위가 다른 시각은 TimePoint로 표현한다.
보고서 스키마와 향후 DB 스키마 변경은 호환성·마이그레이션 테스트를 함께 둔다.
현재 DB 변경은 두 nullable 컬럼 추가다. 범용 버전 관리 마이그레이션 엔진은 아직 없다.

## 서버 운영에서 추가할 것

이번 구조는 macOS 개발과 Linux OCI 실행에서 같은 명령을 사용하도록 유지한다.
실제 24시간 서비스에는 종료 신호 처리, supervisor 설정, 로그 보관/용량 한도, 백업,
재시작 상태 복구와 모니터링 경보가 별도로 필요하다. 현재 실행 시간 상한은 여전히 24시간이며
이 변경으로 무중단 서비스나 실거래 준비가 완료된 것은 아니다.
